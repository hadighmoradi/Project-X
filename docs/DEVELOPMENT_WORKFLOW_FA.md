# روش توسعهٔ Project X

می‌خواهیم روند پیشرفت پروژه روشن و قابل پیگیری باشد. هر مرحله‌ای که به پایان می‌رسد باید در کد، آزمون‌ها، مستندات و صفحه‌های عمومی پروژه به‌درستی ثبت شود.

## پیش از اعلام پایان یک مرحله

- revision دقیق سورس و بخش‌هایی را که تغییر کرده‌اند ثبت کنید.
- سیستم‌عامل، کامپایلر، ابزارها و تنظیمات Build را بنویسید.
- فرمان‌ها و آزمون‌هایی را که واقعاً اجرا شده‌اند فهرست کنید.
- مشخص کنید چه مواردی موفق، ناموفق یا اصلاً آزمایش‌نشده بوده‌اند.
- محدودیت‌های باقی‌مانده و گام بعدی را توضیح دهید.

## وضعیت هر قابلیت را روشن بنویسید

- **Planned – برنامه‌ریزی‌شده:** قابلیتی که برای آینده در نظر گرفته شده است.
- **Designed – طراحی‌شده:** ایده و قواعد آن نوشته شده، اما شاید هنوز پیاده‌سازی نشده باشد.
- **Prototype – نمونهٔ اولیه:** نسخه‌ای آزمایشی وجود دارد، ولی برای استفادهٔ عمومی آماده نیست.
- **Implemented – پیاده‌سازی‌شده:** قابلیت در سورس پروژه وجود دارد.
- **Verified – اعتبارسنجی‌شده:** آزمون‌های مشخص در محیط ثبت‌شده موفق بوده‌اند.
- **Blocked – متوقف:** بخشی که برای ادامه لازم است آماده نیست.
- **Not tested – آزمایش‌نشده:** هنوز آزمونی برای آن مورد اجرا نشده است.

وجود نمونهٔ کد در سند طراحی، پشتیبانی کامپایلر را ثابت نمی‌کند. موفقیت یک آزمایش محدود هم ثابت نمی‌کند همهٔ حالت‌ها درست کار می‌کنند.

## به‌روزرسانی صفحات پروژه

پس از هر Build، تست، Regression، تغییر Runner/Validator، ممیزی Source یا تصمیم فنی مهم، قابلیت انتشار نتیجه را بررسی کنید. هر نتیجهٔ قابل انتشار باید در همان جریان کار در صفحات مرتبط ثبت شود:

- `README.md` و `README_FA.md` برای خلاصهٔ عمومی پروژه؛
- `docs/STATUS.md` و `docs/STATUS_FA.md` برای وضعیت مهندسی جاری؛
- صفحات تاریخچهٔ توسعه برای milestoneهای تکمیل‌شده؛
- راهنمای شروع/Build و طراحی زبان، وقتی دستورها یا ادعاهایشان تغییر می‌کند؛
- صفحات سایت، وقتی وضعیت، نتیجه یا دستورالعمل نمایش‌داده‌شده تغییر می‌کند.

نسخهٔ انگلیسی و فارسی را هماهنگ به‌روز کنید. برای نتیجه‌های مهم تست یا اعتبارسنجی، Milestone تاریخ‌دار اضافه کنید و سوابق قبلی را overwrite نکنید.

## انتشار نتیجه

کاربر مجوز مستمر ساخت Branch، Commit، Push و ایجاد/به‌روزرسانی Pull Request برای تغییرات مناسب Project X را داده است. برای این اقدامات شاخه‌ای درخواست مجوز تکراری نکنید.

روال پیش‌فرض: **Branch → Commit → Push → Pull Request؛ بدون Merge**. ابتدا `main` و PRهای موجود را بررسی کنید؛ از کار تکراری پرهیز کنید؛ پیام Commit روشن بنویسید و پس از انتشار، Branch/Commit/PR را از GitHub بازخوانی و تأیید کنید.

Merge به `main`، نوشتن مستقیم روی `main`، Release/Tag، حذف فایل یا Branch، Force-push/بازنویسی تاریخچه و تغییرات امنیتی/permission نیازمند تأیید جداگانه است.

اگر Source provenance، CI یا Validation لازم کامل نیست، PR را Draft نگه دارید و محدودیت را توضیح دهید. نتیجهٔ تست روی Workspace محلی، اثبات نمی‌کند که `main` عمومی همان Source را دارد؛ برای چنین ادعایی commit SHA و تطبیق کامل Source tree لازم است.

برای روند کامل به [سیاست همگام‌سازی مستمر GitHub](operations/GITHUB_CONTINUOUS_SYNC_POLICY_FA.md) مراجعه کنید.

## قانون اصلی

یک مرحله زمانی تمام‌شده است که کار بررسی شده، نتیجه و محدودیت‌هایش ثبت شده، صفحات مرتبط به‌روز شده و تغییر مناسب در Branch و Pull Request بررسی‌شدهٔ GitHub منتشر شده باشد. Merge خودکار انجام نمی‌شود.
