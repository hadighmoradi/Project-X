# قواعد توسعه و ثبت نتایج Project X

## قانون اصلی

**هر فاز یا checkpoint مهندسی که تکمیل‌شده اعلام می‌شود، باید مستند، اعتبارسنجی و در مخزن GitHub منتشر شود.** به‌روزرسانی فایل‌های Markdown و اطلاعات عمومی پروژه بخشی از تکمیل همان فاز است؛ نباید به زمان نامشخصی در آینده موکول شود.

## چک‌لیست پایان هر فاز

پیش از اعلام تکمیل یک فاز:

۱. **وضعیت دقیق را مشخص کنید.** revision یا commit سورسی که آزموده شده، شناسهٔ checkpoint یا patch و محدودهٔ تغییر را ثبت کنید.

۲. **محیط را بنویسید.** سیستم‌عامل، کامپایلر و نسخهٔ toolchain، تنظیمات Build، سخت‌افزار مؤثر در اندازه‌گیری Performance و وابستگی‌های مهم را درج کنید.

۳. **فقط آزمون‌های واقعاً اجراشده را گزارش کنید.** فرمان‌ها، suiteها، موارد انتخابی، تعدادها و محل گزارش‌ها را بنویسید. موارد PASS، FAIL، SKIP و اجرا‌نشده باید از هم جدا باشند.

۴. **شواهد و مرز اعتبار نتیجه را ثبت کنید.** نتیجه، محدودیت‌ها، اشکال‌های باز، انحراف از برنامه و گام بعدی مشخص را بنویسید. نتیجهٔ یک probe محدود نباید به ادعای پشتیبانی عمومی تبدیل شود.

۵. **مستندات مرتبط را به‌روز کنید.** فایل‌های زیر، بر اساس نوع تغییر، معمولاً باید بررسی و به‌روزرسانی شوند:
   - `docs/STATUS.md` برای آخرین checkpoint اعتبارسنجی‌شده و گام بعدی؛
   - `docs/DEVELOPMENT_HISTORY_FA.md` برای تاریخچهٔ milestoneهای تکمیل‌شده؛
   - `docs/ARCHITECTURE.md` یا سند طراحی زبان برای تغییرات معماری و تصمیم‌های زبان؛
   - ماتریس آزمون/اعتبارسنجی و README در صورت تغییر ادعاها یا دستورهای عمومی پروژه.

۶. **تغییر را منتشر کنید.** تا جای ممکن پیاده‌سازی، آزمون‌ها، گزارش‌ها و مستندات مرتبط با هم commit شوند. برای تغییرات مهم از branch و Pull Request مشخص استفاده کنید و توضیح PR را به checkpoint و شواهد دقیق پیوند دهید.

۷. **اطلاعات عمومی را هماهنگ کنید.** اگر وضعیت، قابلیت، نقشهٔ راه یا تصمیم عمومی تغییر کرد، README و صفحه‌های انگلیسی و فارسی پروژه نیز به‌روز شوند.

## برچسب‌های اجباری وضعیت

این برچسب‌ها به‌صورت یکسان استفاده شوند:

- **Proposed – پیشنهادی:** ایده‌ای که هنوز در حال بررسی است و تأیید نشده.
- **Designed – طراحی‌شده:** طراحی مستند شده، اما ممکن است پیاده‌سازی وجود نداشته باشد.
- **Prototype – نمونهٔ آزمایشی:** پیاده‌سازی محدود یا مستقل وجود دارد، اما اتصال کامل به محصول ثابت نشده.
- **Implemented – پیاده‌سازی‌شده:** قابلیت در سورس پروژه وجود دارد.
- **Verified – اعتبارسنجی‌شده:** پیاده‌سازی مشخص، آزمون‌های مشخص را در محیط ثبت‌شده با موفقیت گذرانده است.
- **Not ready / Blocked – آماده نیست / مسدود:** gate لازم پاس نشده یا وابستگی حل‌نشده وجود دارد.
- **Not run – اجرا نشده:** آزمون انجام نشده است؛ هرگز نباید موفقیت آن القا شود.

صرف وجود نحو در سند طراحی یا اجرای یک حالت کنترل‌شده در Prototype، به معنی پشتیبانی عمومی آن قابلیت نیست.

## شواهد و قابلیت پیگیری

گزارش پایان فاز باید به توسعه‌دهندهٔ دیگر امکان دهد به این سؤال‌ها پاسخ دهد:

- کدام revision دقیق سورس بررسی شده است؟
- در این مرحله چه چیزی تغییر کرده است؟
- چه فرمان‌های Build و آزمونی اجرا شده‌اند؟
- چه چیزی موفق، ناموفق یا اجرا‌نشده بوده است؟
- محدودیت‌ها و موانع باقی‌مانده چیست؟
- کدام commit، Pull Request، گزارش و صفحهٔ Markdown نتیجه را توضیح می‌دهند؟

revision سورس آزموده‌شده و commit/PR انتشار را به هم پیوند دهید. تلاش نکنید hash کامیتی را که همان لحظه در حال ساخته‌شدن است داخل خودش بنویسید؛ لینک commit یا PR نهایی را در گزارش فاز یا به‌روزرسانی بعدی وضعیت قرار دهید.

## تصمیم‌های طراحی و مهندسی

- هدف محصول، پیشنهاد طراحی، تصمیم تأییدشده، Prototype و پیاده‌سازی اعتبارسنجی‌شده باید از هم جدا بمانند.
- هرجا تصمیم کاربر لازم است، گزینه‌ها را مستند کنید و منتظر تأیید صریح بمانید؛ پیشنهاد باز را بی‌صدا به تصمیم قطعی تبدیل نکنید.
- پس از تأیید تصمیم طراحی، سند طراحی و در صورت لزوم خلاصهٔ عمومی را به‌روز کنید.
- هنگام تغییر پیاده‌سازی، کد، آزمون‌ها و مستندات مرتبط را تا حد امکان با هم به‌روز کنید.
- اگر Full Regression اجرا نشده است، آن را شفاف بنویسید؛ حتی اگر آزمون‌های محدود موفق بوده‌اند.

## ایمنی مخزن و حفظ تاریخچه

- سوابق تاریخی، manifestها، گزارش آزمون و آرشیوهای بازیابی را حفظ کنید؛ آن‌ها را بی‌اجازه حذف یا جایگزین نکنید.
- تغییرات افزایشی و قابل بازبینی را ترجیح دهید. در Patch عملکردی، قالب‌بندی گسترده یا پاک‌سازی نامرتبط انجام ندهید.
- برای تغییرات مهم branch و Pull Request بسازید. تا وقتی مالک مخزن تأیید نکرده است، PR جدید را در `main` ادغام نکنید؛ مگر اینکه مالک صریحاً دستور دیگری داده باشد.
- Workspace محلی و مخزن GitHub باید از طریق patch/commit قابل شناسایی هماهنگ بمانند. به‌روزرسانی GitHub به معنی تغییر خودکار Workspace محلی Windows کاربر نیست.

## تعریف واقعی تکمیل فاز

یک فاز زمانی تکمیل‌شده است که معیارهای فنی پذیرش را گذرانده باشد، شواهد آن ثبت شده باشد، فایل‌های Markdown و خلاصه‌های عمومی مرتبط به‌روز شده باشند و تغییر نهایی به‌صورت commit در GitHub منتشر شده باشد. تا وقتی یکی از این مراحل باقی است، وضعیت باید «در انتظار انتشار» گزارش شود، نه «تکمیل‌شده».
