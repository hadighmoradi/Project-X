# ایدهٔ اصلی زبان Project X

می‌خواهم کار با X ساده و راحت باشد، برنامه‌های Native بسازد و هم برای نرم‌افزارهای روزمره مناسب باشد و هم برای کارهای سیستمی. هدف این است که برنامه‌نویسی آسان‌تر شود، بدون اینکه کنترل کافی روی برنامهٔ نهایی را از دست بدهیم.

X هنوز در حال توسعه است. در این صفحه دربارهٔ مسیر طراحی و ایده‌هایی که از زبان‌ها و ابزارهای دیگر گرفته‌ایم صحبت می‌کنیم. وجود یک قابلیت در این صفحه به معنی آماده‌بودن آن در کامپایلر فعلی نیست.

## چه چیزهایی برایمان مهم است؟

**کدنویسی ساده و خوانا:** کدهای معمولی باید روشن باشند. برای انجام کارهای ساده نباید با نحو پیچیده روبه‌رو شویم.

**اجرای سریع و Native:** برنامه باید به خروجی Native کامپایل شود. برای سنجش سرعت، آن را با برنامه‌های هم‌ارز C و C++ مقایسه می‌کنیم؛ نه با ادعاهای بدون آزمون.

**فایل اجرایی کم‌حجم:** یک برنامهٔ کوچک نباید مجبور باشد Runtime بزرگ یا کتابخانه‌هایی را که استفاده نمی‌کند همراه خود ببرد.

**قدرت و کنترل:** با پیشرفت پروژه، باید بتوان با X کارهای سیستمی، مدیریت منابع و برنامه‌های Windows را هم انجام داد.

## از زبان‌های دیگر چه چیزهایی یاد می‌گیریم؟

زبان‌ها و ابزارهایی را بررسی کرده‌ام که هرکدام در یک زمینه خوب عمل می‌کنند. هدف، یادگرفتن از آن‌هاست؛ نه کپی‌کردن کامل یک زبان.

| زبان یا ابزار | ویژگی خوب آن | چیزی که می‌خواهیم در X داشته باشیم |
|---|---|---|
| **Visual Basic** | نحو ساده و خوانا | کدنویسی روزمره راحت و قابل‌فهم باشد |
| **C** | دسترسی مستقیم به سیستم و عملکرد Native | کنترل سطح پایین حفظ شود و C معیار مقایسهٔ سرعت باشد |
| **Delphi / Lazarus** | محیط توسعهٔ کامل و طراحی بصری فرم‌ها | ساخت برنامه‌های Windows با IDE و Form Designer راحت باشد |
| **Python** | کد ساده و کتابخانه‌های سطح‌بالا | کارهای رایج آسان باشند، بدون نیاز اجباری به مفسر Python |
| **Rust** | توجه به نوع‌ها، خطاها و مالکیت منابع | طول عمر منابع و خطاها روشن و قابل پیش‌بینی باشند |
| **Windows Batch / CMD** | دستورهای کوتاه برای فایل، پوشه و اجرای برنامه‌ها | کارهای معمول سیستمی API ساده و مشخص داشته باشند |
| **PureBasic** | ساخت مستقیم و سادهٔ برنامه‌های گرافیکی | کار با GUI برای برنامه‌نویس راحت باشد |

C و C++ همچنین معیارهای مهمی برای مقایسهٔ عملکرد Native و دسترسی سطح پایین هستند. قرار نیست نحو آن‌ها را در همه‌چیز عیناً تکرار کنیم.

## نمونه‌ای از شکل کدنویسی

فایل‌های سورس با پسوند .src و با متن UTF-8 نوشته می‌شوند. بلوک‌ها آکولاد دارند، دستورها با سمی‌کالن تمام می‌شوند و تعریف تابع با function شروع می‌شود.

    function Add(left, right) {
        return left + right;
    }

    function Welcome() {
        PrintLine "به زبان X خوش آمدید.";
    }

شرط هم به همین شکل نوشته می‌شود:

    if (ready) {
        PrintLine "آماده است";
    } else {
        PrintLine "لطفاً صبر کنید";
    }

برای فرم‌های Windows دو فایل مرتبط در نظر گرفته‌ایم: فایل .frm ظاهر و اجزای فرم را توصیف می‌کند و فایل .src کنار آن، کد برنامه و تابع‌های رویداد را در خود دارد.

    Form MainForm {
        Caption = "فهرست مشتریان";
        ClientWidth = 700;
        ClientHeight = 450;

        Button SaveButton {
            Caption = "ذخیره";
            OnClick = HandleSave;
        }
    }

این قالب، شکل موردنظر برای فایل فرم است. طراح بصری و اتصال کامل آن به کامپایلر هنوز در حال توسعه‌اند.

## سرعت و حجم کم از کجا می‌آیند؟

حجم کم فایل اجرایی را از یک زبان خاص نمی‌گیریم؛ این موضوع به شیوهٔ ساخت کامپایلر و کتابخانه‌ها بستگی دارد.

در طراحی فعلی، کامپایل Native، Static Linking به‌عنوان روش پیش‌فرض و Runtime ماژولار در نظر گرفته شده‌اند. برنامه فقط باید بخش‌هایی از کتابخانه را وارد خروجی کند که واقعاً به آن‌ها نیاز دارد. فایل‌های طراحی مانند .frm نیز باید هنگام طراحی یا Build پردازش شوند، نه در هر بار اجرای برنامهٔ نهایی.

البته Static Linking به‌تنهایی کوچک‌بودن فایل را تضمین نمی‌کند. کامپایلر، linker، کتابخانه‌ها و خود برنامه روی حجم خروجی اثر دارند. برای سنجش واقعی باید اندازهٔ فایل، زمان شروع و سرعت اجرا را با آزمون‌های تکرارپذیر اندازه بگیریم.

## کامپایلر عمومی فعلی چه کاری انجام می‌دهد؟

کد فعلی مخزن، یک frontend آزمایشی با C++17 و یک backend اختصاصی x64 است. مسیر یکپارچهٔ فعلی برای Windows x64 به این شکل است:

    متن سورس
        |
        v
    parse_source
        |
        v
    CompilationUnit
        |
        v
    compile_x64_coff_program
        |
        v
    ماژول‌های AMD64 COFF و link plan
        |
        v
    لینکِر Windows
        |
        v
    فایل اجرایی PE32+

این بخش، یک قسمت واقعی اما محدود از برنامهٔ بزرگ‌تر ماست. زبان X، Runtime، کتابخانهٔ استاندارد، IDE و Form Designer هنوز به شکل محصول کامل آماده نیستند.

## وضعیت فعلی و گام بعدی

جدیدترین اعتبارسنجی ثبت‌شده، **Full Regression برای N114 v10.63 در ۲۷ نوامبر ۲۰۲۶** است که توسط کاربر در Workspace محلی Windows/MSVC اجرا شده است.

- موجودی تعریف‌شدهٔ تست: **۱۷۵٬۹۷۶ از ۱۷۵٬۹۷۶ موفق** در ۲۶ Batch معتبر.
- ماتریس Build ویندوز: **۹ از ۹ هدف** با کد خروجی صفر و NMake به‌صورت Serial.
- شناسه‌های تست: ۱۷۵٬۹۷۶ شناسهٔ یکتا، بدون شناسهٔ ناموفق یا Duplicate درون/بین Batchها.
- هر هفت Source SHA-256 Guard نام‌برده موفق بوده‌اند.
- G9 همچنان Statement-edge-only، مقدار G10 همچنان do-not-rebuild و مقدار G11 برابر ۰ از ۷ است.
- مقدار `spill_call_crossing=true` است و XMM non-empty همچنان open / blocked-not-proven-impossible باقی مانده است.
- این شواهد Edge Bundle insertion یا اجرای End-to-End فایل PE تولیدشده را ثابت نمی‌کنند.

**محدودیت منشأ سورس:** Runner، SHA مربوط به commit سورس را ثبت نکرد. بررسی فقط‌خواندنی نشان داد Source محلی آزموده‌شده با درخت `main` عمومی که برای این رکورد بررسی شد، یکسان نیست. بنابراین Full Regression مدرکی برای Workspace محلی و موجودی تعریف‌شدهٔ آن است و اثبات نمی‌کند سورس عمومی فعلی byte-for-byte همان نسخه باشد. همگام‌سازی کامل درخت Source عمومی همچنان باقی است. به [رکورد Full Regression مربوط به N114](milestones/PROJECT_X_N114_V10_63_FULL_REGRESSION_WINDOWS_MSVC_2026-11-27_FA.md) و [وضعیت مهندسی جاری](STATUS_FA.md) مراجعه کنید.
