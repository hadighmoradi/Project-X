# معرفی طراحی زبان Project X

> زبانی خوانا که به برنامه‌های Native کامپایل می‌شود و بر رفتار قابل پیش‌بینی و خروجی جمع‌وجور تمرکز دارد.

این صفحه خلاصه‌ای عمومی و ساده از مسیر طراحی زبان است که از اسناد معماری و نحو پروژه تهیه شده است. این صفحه مشخصات کامل زبان نیست و به این معنی هم نیست که تمام قابلیت‌های طراحی‌شده در کامپایلر فعلی پیاده‌سازی شده‌اند.

## چه زبانی می‌خواهیم بسازیم؟

هدف بلندمدت ما جمع‌کردن سه خواسته در کنار هم است:

۱. **کدنویسی ساده و خوانا:** نوشتن و خواندن برنامه‌های روزمره نباید دشوار باشد.

۲. **اجرای Native:** برنامه پس از کامپایل مستقیماً روی سیستم‌عامل اجرا شود و کارایی آن در workloadهای یکسان با C/C++ مقایسه‌پذیر باشد.

۳. **خروجی کم‌حجم:** برای استفاده از یک قابلیت ساده، فایل اجرایی نباید مجبور باشد مفسر یا تمام کتابخانه‌های استفاده‌نشده را همراه خود داشته باشد.

این موارد هدف‌های مهندسی‌اند. سرعت، اندازهٔ فایل اجرایی، زمان شروع، سازگاری و پایداری باید روی نسخه و workload مشخص اندازه‌گیری شوند؛ تا آن زمان نباید آن‌ها را نتیجهٔ اثبات‌شده معرفی کنیم.

## از هر زبان چه ایده‌ای می‌گیریم؟

در اسناد طراحی پروژه، چند زبان و ابزار شناخته‌شده برای مقایسه و الهام بررسی شده‌اند. منظور، استفاده از ایده‌های خوب است؛ نه کپی کامل نحو، پیاده‌سازی، کد یا مجوز آن زبان‌ها.

| زبان یا ابزار | نکتهٔ مثبت مورد توجه | چیزی که می‌خواهیم در X داشته باشیم |
|---|---|---|
| **Visual Basic** | سادگی و قابل‌فهم‌بودن نحو | کدهای معمولی خوانا باشند و تشریفات غیرضروری نداشته باشند |
| **Python** | APIهای سطح‌بالا و روشن و راحتی کارهای روزمره | عملیات رایج کتابخانه‌ای ساده باشند، بدون نیاز به مفسر پویا برای اجرای برنامه |
| **C / C++** | قدرت Native، کنترل سطح پایین، Stream و معیار جدی برای مقایسهٔ سرعت | دسترسی سیستمی و کنترل کافی حفظ شود و کارایی با برنامه‌های هم‌ارز C/C++ سنجیده شود |
| **Rust** | توجه به نوع‌ها، خطاهای روشن، مالکیت و طول عمر منابع | رفتار منابع قابل پیش‌بینی و قرارداد APIها دربارهٔ مالکیت و خطا واضح باشد |
| **Windows Batch / CMD** | دستورهای مستقیم برای فایل، پوشه، متغیر محیطی، آرگومان و فرایند | عملیات ساده و نام‌دار داشته باشیم، اما نحو شکننده CMD و اجرای ضمنی Shell را وارد زبان نکنیم |
| **PureBasic** | تجربهٔ ساده و مستقیم برای ساخت GUI | APIهای رابط گرافیکی قابل‌فهم و مسیر طراحی بصری فرم داشته باشیم |
| **Delphi / Lazarus** | محیط توسعهٔ یکپارچه و Form Designer بصری | تجربهٔ IDE و طراحی فرم را به‌عنوان الگوی محصول بررسی کنیم |

در آخرین خلاصهٔ فشردهٔ معماری، **Visual Basic، C و Delphi/Lazarus** به‌عنوان الهام‌های اصلی نام برده شده‌اند. در یادداشت‌های مقایسه‌ای قدیمی‌تر، **Python، Rust، Windows Batch/CMD و PureBasic** نیز برای طراحی APIها و تجربهٔ GUI بررسی شده‌اند. این منابع ممکن است با بازبینی طراحی تغییر کنند.

## نمونه‌ای ساده از شکل نوشتن کد

مرجع فشردهٔ نحو، قواعد قابل مشاهده‌ای مانند فایل سورس `.src`، متن UTF-8، آکولاد برای بلوک‌ها، سمی‌کالن در پایان دستور و کلیدواژهٔ `function` را مشخص می‌کند:

```x
function Add(left, right) {
    return left + right;
}

function PrintWelcome() {
    PrintLine "به زبان X خوش آمدید.";
}
```

شرط نیز از همان شکل بلوکی استفاده می‌کند:

```x
if (ready) {
    PrintLine "آماده است";
} else {
    PrintLine "لطفاً صبر کنید";
}
```

این نمونه‌ها شکل موردنظر نحو را توضیح می‌دهند؛ به معنی پشتیبانی کامپایلر عمومی فعلی از تمام امکانات سند طراحی نیستند.

## چرا انتظار داریم فایل اجرایی کوچک باشد؟

**حجم کم خروجی را از یک زبان خاص کپی نمی‌کنیم.** این هدف با چند انتخاب مهندسی دنبال می‌شود:

- کامپایل Native، به‌جای اینکه برای اجرای هر برنامه نصب مفسر لازم باشد.
- انتخاب Static Linking به‌عنوان روش پیش‌فرض Build.
- ماژولار بودن Runtime و کتابخانه‌ها تا فقط بخش‌های لازم وارد Build شوند.
- نیاز نداشتن فایل اجرایی نهایی به Parser زمان اجرا برای فایل‌های طراحی مانند `.frm`.
- اندازه‌گیری تکرارپذیر اندازهٔ فایل اجرایی، زمان شروع و سربار اجرا.

Static Linking به‌تنهایی کوچک‌بودن خروجی را تضمین نمی‌کند. نتیجه به کامپایلر، linker، کتابخانه‌های انتخاب‌شده، Runtime، بهینه‌سازی و خود برنامه بستگی دارد.

## معماری Native؛ هدف طراحی و کد فعلی

در چشم‌انداز نهایی، سورس و اطلاعات طراحی به خروجی Native تبدیل می‌شوند. اما مخزن عمومی فعلی مسیر محدودتری را نشان می‌دهد:

```text
مسیر کامپایلر عمومی فعلی

متن سورس
   |
   v
parse_source
   |
   v
CompilationUnit
   |
   v
compile_x64_coff_program
   |
   v
ماژول‌های AMD64 COFF + طرح پیوند قطعی
   |
   v
لینکر سیستم‌عامل
   |
   v
فایل اجرایی Windows x64 از نوع PE32+
```

Backend فعال در مخزن عمومی، پیاده‌سازی اختصاصی x64 است و LLVM نیست. snapshot کامپایلر هنوز آزمایشی است و نمایندهٔ زبان کامل، Runtime، کتابخانهٔ استاندارد، IDE یا محصول GUI نهایی نیست.

## GUI و Form Designer بصری

در طراحی زبان، دو فایل مرتبط در نظر گرفته شده‌اند:

- `.src`: کد برنامه و تابع‌های رسیدگی به رویدادها.
- `.frm`: توصیف declarative فرم و اجزای ظاهری آن.

فایل `.frm` برای مرحلهٔ طراحی و Build در نظر گرفته شده است؛ نه یک Script عمومی که هر فایل اجرایی نهایی مجبور به تفسیر آن باشد. Designer بصری، چرخهٔ عمر Componentها، اتصال به Runtime و Parser تولیدی هنوز نیازمند تکمیل و اعتبارسنجی‌اند.

## تا امروز چه چیزی واقعاً انجام شده است؟

**آخرین checkpoint عمومی: N113-G62R16 · ۲۳ نوامبر ۲۰۲۶**

- snapshot چهارده‌فایلی G62R16 با فایل‌های متناظر در Workspace تطبیق دارد.
- آزمایش محدود G62R13 با MSVC و G2-on روی workload کنترل‌شده موفق بوده است: ۵۶ action، ۶۶ machine move و ۴۷۴ بایت انتقال.
- درج عمومی edge آماده نیست: مقدار G11 برابر ۰ از ۷ است و عملیات insertion انجام نشده است.
- Full Regression برای این checkpoint اجرا نشده است.
- گام بعدی ثبت‌شده G62R17 است: بررسی liveness موقت‌های expression و مالکیت register پیش از طراحی routing اختیاری. این مرحله هنوز انجام نشده است.

وضعیت پلتفرم‌ها نیز محدود است:

| هدف | وضعیت مستندشده در مخزن عمومی |
|---|---|
| Windows x64 | مسیر یکپارچهٔ فعلی ماژول AMD64 COFF و link plan می‌سازد؛ linker سیستم‌عامل PE32+ تولید می‌کند |
| Linux x64 | اجزای ELF64 و شواهد محدود LLD روی میزبان Linux وجود دارند؛ مسیر کامل سورس تا ELF اثبات نشده است |
| x86-32 | هدف نقشهٔ راه است؛ در Backend فعلی پیاده‌سازی نشده |
| macOS | هدف آینده است؛ خروجی Mach-O و اعتبارسنجی macOS اثبات نشده‌اند |
